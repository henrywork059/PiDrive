## Root cause
Keyboard shortcuts at overlapping Qt scopes caused duplicate ownership; callback-only text guards prevented annotation actions but could still swallow typed keys. The canvas modified `PixelBox` instances directly without capturing undo snapshots, with right-drag issuing one change signal on release but no history. The image always fitted to the available canvas, making precise placement of small objects difficult.

## Limits, persistence and release gate
- Undo only tracks edits to the **current in-memory frame**. It does not undo a frame-file deletion, cross-frame edits after frame switching, previous manual saves on an already-closed frame, or Quick Deploy's batch writes to other frames. Existing explicit label saves and autosave on frame switch remain authoritative.
- The undo/redo stack is cleared when an image is loaded or reloaded. Zoom/pan are visual only and reset on image switch. At original 1× zoom, middle-drag cannot move the picture outside its fitted bounds.
- New direct number shortcuts cover at most the first nine classes. Existing W/S and class drop-down support any number of classes; no class IDs/schema changed.
- Real-Qt check before promotion on Windows: `cd CustomTrainer && python -m unittest discover -s tests -v`; check A/D, PageUp/Down, class W/S/1..9, B/Shift+B, typing `adsw123` in every line/plain-text field, Ctrl+Z/Y/Ctrl+Shift+Z with drawing/deletion/move/drag/class changes, zoom/pan at different window sizes, undo after current-frame Quick Deploy, Quick Deploy selected/current frame and 280px right pane after saved splitter restore. Confirm no shortcut fires while editing text.
- No changes to U27 model manifests, U25 immutable cache locks, U18 splitting/labels validator, class names on disk, export pages, Pi runtime, or legacy PiCar.
